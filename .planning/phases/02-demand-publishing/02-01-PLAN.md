# Plan: 02-01 — Demands Database Schema

**Goal:** Implement the persistence layer for service demands with spatial support and security.

**Requirements:** DEMD-01, DEMD-02, DEMD-03

**Context:**
- Needs `demands` table in Supabase.
- Must support spatial queries via PostGIS for radius-based visibility.
- RLS must ensure contractors only manage their own demands.

**Proposed Changes:**

1. **Supabase Migration:**
   - Create `supabase/migrations/20260428000000_create_demands.sql`.
   - Enable `postgis` extension (if not already enabled, though usually it is).
   - Create `demand_status` enum: `aberta`, `em_contato`, `encerrada`.
   - Create `demand_urgency` enum: `baixa`, `media`, `alta`, `urgente_hoje`.
   - Create `demands` table:
     - `id` (uuid, PK)
     - `contractor_id` (text, FK to `profiles.clerk_user_id`)
     - `service_type` (text)
     - `description` (text)
     - `municipality` (text)
     - `location` (geography(POINT, 4326))
     - `urgency` (demand_urgency)
     - `visibility_radius` (integer, in km)
     - `status` (demand_status, default 'aberta')
     - `created_at`, `updated_at`
   - Add GiST index on `location`.
   - Add RLS policies:
     - `SELECT`: All authenticated users (or according to visibility rules, but for now let's say all authenticated can see open demands).
     - `INSERT`: Authenticated users can insert if `contractor_id` matches their JWT sub.
     - `UPDATE`: Authenticated users can update if `contractor_id` matches their JWT sub.

**Verification Plan:**

1. **Database Verification:**
   - Run `supabase db push` (simulated or actual if environment allows).
   - Check if table and enums exist.
   - Verify GiST index is created.
2. **RLS Verification:**
   - Test inserting a demand with a different `contractor_id` (should fail).
   - Test updating another user's demand (should fail).
   - Test selecting own demands (should succeed).
